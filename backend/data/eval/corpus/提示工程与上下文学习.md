# 提示工程与上下文学习

## 提示词的基本结构

对话式大模型的消息分角色：**system**（角色与规则设定，全程生效）、**user**（任务指令）、**assistant**（模型回复）。提示工程的第一原则：**把要求写具体**——

- 模糊："帮我总结一下" → 明确："用三点总结，每点不超过 30 字，面向不懂技术的读者"
- 指定输出格式（编号列表、JSON、指定字段名），模型输出的结构化程度直接来自指令的结构化程度
- 给出约束与边界（字数、语气、禁止事项）比只给目标更有效
- 无关背景会稀释注意力：只保留完成任务必需的上下文

## 上下文学习（ICL）与少样本提示

不更新参数，直接在提示词里放若干**输入→输出示例**，让模型照着模式完成新输入：
- 示例数量：通常 2~5 个即可显著改善格式与风格对齐
- 示例顺序有影响：最新的/最相关的放最后更易被模仿
- 示例要覆盖任务的典型形态，包含边界情况效果更好

## 思维链（Chain-of-Thought）

让模型**先写出逐步推理再给答案**，而不是直接猜结果：
- 零样本写法："让我们一步一步思考" / "先分析条件，再列式计算，最后给出答案"
- 少样本写法：示例中演示完整推理过程（不只是答案对）
- 收益场景：数学、逻辑推理、多步规划——答案正确率显著提升
- 变体：自我一致性（多次采样推理路径后投票取多数答案）、自查（生成后再让模型检查一遍中间步骤）

## 结构化生成与自检

- 要求模型先输出固定标记再输出正文，可被程序解析（评测与流水线常用）
- 关键任务采用"生成 → 评审"两段式：先产出草稿，再用另一条提示让模型按清单自检（事实性、完整性、格式）
- 输出要求里显式声明"若信息不足直接说明，不要编造"，能有效压制瞎编倾向

## 提示词的失效与对策

- 指令过长过杂 → 拆成多轮或多步流水线
- 模型忽略部分指令 → 把最重要的要求放在首尾（中间内容注意力最弱）
- 任务需要外部知识 → 提示词本身解决不了知识缺口，需要把资料片段直接放进上下文再让它据此作答
